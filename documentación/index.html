Arquitectura del Sistema

Diseño modular en capas desacopladas siguiendo las mejores prácticas de Spring Boot

Cuquora CRM implementa una arquitectura monolítica modular diseñada para alta cohesión y bajo acoplamiento. Se compone de un motor Spring Boot 3.3 ejecutándose sobre Java 17/21, persistencia relacional con JPA/Hibernate, motor de plantillas server-side Thymeleaf enriquecido con componentes interactivos JavaScript y estilos CSS desacoplados.

Capa Arquitectónica Componentes Principales Responsabilidad y Tecnologías
Presentación / Vistas Thymeleaf, HTML5 Semántico, CSS3 Vanilla modular Renderizado dinámico de vistas responsivas, modales unificados, selector de franjas horarias y layout adaptativo.
Controladores Web & API BaseController, AppointmentController, InventoryController, CenterApiController Gestión de peticiones HTTP, validación de parámetros, orquestación de sesión HTTP y exposición de endpoints REST JSON con cálculo geográfico Haversine.
Lógica de Negocio (Servicios) AppointmentService, InventoryService, TreatmentService, UserService, NotificationService, EmailService Validación matemática de disponibilidad de cabinas (intervalos de 30 min), prevención de roturas de stock, emisión de alertas proactivas, encriptación BCrypt y canal de comunicación por correo transaccional (Spring Mail / EmailJS).
Acceso a Datos (Repositorios) Spring Data JPA, CrudRepository / JpaRepository Consultas JPQL optimizadas para búsqueda espacial, filtrado por centro, ordenación cronológica y transacciones atómicas (@Transactional).
Persistencia & Datos PostgreSQL 16 (Producción / Docker) o H2 Database (Desarrollo) Esquema relacional íntegro con claves foráneas en cascada, unicidad de stock por producto/centro y script automatizado init.sql.
💡
Principio de Aislamiento por Sede:

Cada centro de belleza dispone de su propio almacén de inventario y sus propios tratamientos asignados. El catálogo de productos es global, pero las existencias, umbrales y alertas se calculan de manera independiente por cada sede física.

Modularización y Reparto de CSS por Vista

Estrategia de desacoplamiento de estilos para optimizar rendimiento y eliminar redundancias

Originalmente, la aplicación concentraba estilos en archivos monolíticos (como home.css de más de 72 KB con estilos de landing y autenticación mezclados) y cargaba hojas de estilo cruzadas innecesarias en vistas secundarias. Se llevó a cabo una reorganización integral para que cada plantilla HTML importe única y exclusivamente los estilos que consume:

Archivo CSS Propósito y Dominio Vistas que lo Importan Optimización Realizada
common.css Design System global, variables CSS (colores champagne/lux, fuentes Playfair y Plus Jakarta Sans), navbar y pie de página. Todas las vistas HTML Capa base inmutable y compartida con cero estilos específicos de página.
auth.css Tarjetas de autenticación glassmorphism (.auth-card), inputs, alternador de contraseña, selectores de rol y alertas de error/éxito. login.html, register.html, login-selector.html Nuevo archivo extraído: Se retiraron ~500 líneas de home.css, reduciendo drásticamente la carga de red en autenticación.
home.css Landing page comercial estilo SaaS (Hero, pipeline de 4 pasos, tarjetas interactivas de cabinas y monitor de agenda en tiempo real). landing.html Depurado: exclusivo para la página de inicio comercial, eliminando estilos de autenticación que no le correspondían.
treatments.css Catálogo de tratamientos de cabina (.treatment-item-card), botón flotante (FAB) móvil y transformación a Bottom-Sheet. worker/treatments.html Nuevo archivo extraído: Desacoplado de worker.css, evitando que el dashboard descargue código de modales de servicios.
worker.css Panel principal del empleado: banner de bienvenida, métricas clave, rejilla de accesos rápidos y contadores analíticos. worker/dashboard.html Eliminación de bloques duplicados de .action-card y exclusión de las vistas de clientes que no lo usaban.
calendar.css Rejilla interactiva mensual de citas, selección de día, filtros de estado y tarjetas de agenda con feedback. worker/calendar.html Autosuficiente: absorbió los badges y botones necesarios, eliminando la dependencia de clients.css (24 KB).
clients.css Cartera de clientes, tarjetas de contacto, fichas técnicas dinámicas y editor visual de la plantilla de ficha del centro. worker/clients.html, client_detail.html, client_card_template.html Eliminada la importación residual de worker.css en estas tres pantallas.
cliente.css / citas.css Portal de reservas de cliente, selección de centro, mapas y consulta de historial de citas confirmadas. client/centers.html, center_details.html, booking.html, appointments.html Mantenidos independientes y combinados con modals.css y datepicker.css según necesidad real.

Auditoría Arquitectónica de Principios SOLID

Evaluación del diseño orientado a objetos del backend Java / Spring Boot

Se ha completado una inspección rigurosa del código fuente del backend frente a los 5 principios fundamentales de diseño de software (SOLID), detectando los siguientes puntos de fricción arquitectónica y sus planes de refactorización recomendados:

S — Single Responsibility

Responsabilidad Única

Hallazgos:

  • BaseController orquesta landing comercial, validación de registro de usuarios, autenticación en sesión HTTP y simulador de depuración.
  • ClientCardService procesa serialización JSON de plantillas, operaciones CRUD de fichas y consolidación analítica de clientes a partir del histórico.
  • AppointmentService mezcla validación de horarios y persistencia con mapeo manual de entidades a AppointmentCalendarDTO.
Remediación: Separar en LandingController, AuthController y DevSessionController; extraer AppointmentMapper y desacoplar ClientCardTemplateService.
O — Open/Closed

Abierto para Extensión / Cerrado para Modificación

Hallazgos:

  • Bifurcaciones if/else basadas en Strings ("CLIENT" vs "WORKER") en controladores; agregar un rol (ej. ADMIN) obliga a modificar código existente en múltiples clases.
  • Horarios laborales (L-V 09:00 - 20:00, slots de 30 min) hardcodeados en el método privado isWithinOpeningHours de AppointmentService.
  • Reglas de notificación (stock ≤ 3, citas pendientes) centralizadas en un solo método rígido en NotificationService.
Remediación: Implementar patrón Strategy con interfaz NotificationProvider, extraer SchedulePolicy asociada a la entidad Center y gestionar roles con Spring Security GrantedAuthority.
L — Liskov Substitution

Sustitución de Liskov

Hallazgos:

  • Inyección de identidades fijas en la simulación de sesión de BaseController (asignación estática de ID 3L sin validar existencia previa en BD).
  • ClientSummaryDTO modelaba indistintamente clientes registrados y fichas sin usuario, obligando a verificaciones defensivas != null para prevenir NullPointerException.
Remediación: Emplear un contexto de sesión fuertemente tipado (UserSessionPrincipal) con invariantes garantizados.
I — Interface Segregation

Segregación de Interfaces

Hallazgos:

  • Ausencia de interfaces en los servicios de negocio (AppointmentService, ClientCardService, etc.); los controladores se acoplan a la clase concreta completa.
  • Interfaces amplias en repositorios: AppointmentRepository agrupa 14 métodos con propósitos muy distintos (operativa de reserva, analítica, agenda y borrado masivo).
Remediación: Descomponer servicios en interfaces orientadas al caso de uso: AppointmentBookingService, AppointmentScheduleQueryService y AppointmentManagementService.
D — Dependency Inversion

Inversión de Dependencias

Hallazgos:

  • Los controladores dependen directamente de implementaciones concretas en vez de abstracciones o contratos (IAppointmentService, IUserService).
  • ClientCardController inyecta y consulta directamente ClientCardRepository, saltándose por completo la capa de servicio (bypass arquitectónico).
  • ClientCardService instancia directamente new ObjectMapper() en lugar de inyectar el bean administrado por el contenedor IoC de Spring.
Remediación: Inyectar ObjectMapper a través del constructor, encapsular los repositorios exclusivamente dentro de servicios y desacoplar controladores mediante interfaces.

Modelo de Dominio y Entidades

Estructura relacional de base de datos que sustenta la plataforma

🏢 Center (Centros de Belleza)

Representa una sede física. Contiene nombre, dirección física, teléfono, email de contacto y coordenadas geográficas (latitud y longitud) para el cálculo de distancia en tiempo real.

👤 User & Role (Usuarios y Roles)

Entidad de usuarios del sistema. Posee nombre, email único, teléfono, contraseña cifrada en BCrypt y asignación a un Role (CLIENT o WORKER). Los trabajadores se vinculan a un Center.

💆 Treatment (Catálogo de Servicios)

Tratamientos ofrecidos por cada centro. Incluye nombre, descripción, tarifa (€), duración estimada en minutos (30, 45, 60, 90) y tipología (FACIAL, MASAJES, MANICURA_PEDICURA, CORPORAL, etc.).

📦 Product & Inventory (Insumos y Stock)

Product es el catálogo maestro (nombre, descripción, categoría, PVP). Inventory gestiona las existencias en cada sede con restricción de unicidad (center_id, product_id).

📋 ClientCard & Template (Fichas Técnicas Dinámicas)

Motor de fichas técnicas personalizadas por centro. ClientCardTemplate almacena en JSON la estructura de campos configurables (soportando tipos text, textarea, select, checkbox, date y el nuevo tipo number). ClientCard almacena las respuestas y notas técnicas del especialista por cliente.

📅 Appointment (Citas y Reservas)

Registra el turno acordado. Vincula un dateTime (fecha y hora exacta), un treatment, un center y obligatoriamente un client registrado (cuenta de usuario activa), el worker asignado, su estado (PENDING, CONFIRMED, REJECTED) y el workerMessage para feedback médico-estético. Nota: El flujo de clientes invitados ha sido suprimido para garantizar trazabilidad e integridad técnica de las fichas.

Puesta en Marcha del Proyecto

Instrucciones para levantar la aplicación en entorno local o mediante Docker

Opción A: Ejecución con Docker Compose (Recomendada con PostgreSQL)

Levanta el servidor web Spring Boot y la base de datos PostgreSQL 16 con los datos iniciales de init.sql ya sembrados:

# Clonar el repositorio y situarse en la raíz del proyecto
cd CRM_CBelleza

# Construir y levantar los contenedores en segundo plano
docker-compose up --build -d

# Visualizar logs del servicio web
docker-compose logs -f app

La aplicación estará accesible en: http://localhost:8080

Opción B: Ejecución Local con Maven y Java 17+

# En Windows PowerShell
./mvnw.cmd spring-boot:run

# En Linux / macOS
./mvnw spring-boot:run

Al arrancar localmente sin variables de entorno de PostgreSQL, Spring Boot arrancará con su base de datos en memoria H2 y ejecutará automáticamente DatabaseSeeder.java, precargando los centros, usuarios, citas, catálogo y stock.
