Arquitectura del Sistema

Diseño modular en capas desacopladas siguiendo las mejores prácticas de Spring Boot

Cuquora CRM implementa una arquitectura monolítica modular diseñada para alta cohesión y bajo acoplamiento. Se compone de Spring Boot 4.1 sobre Java 21 con Spring Security, persistencia relacional con JPA/Hibernate y esquema versionado con Flyway, plantillas Thymeleaf en el servidor con JavaScript sin framework y estilos CSS propios a partir de unos tokens de diseño.

Capa Arquitectónica Componentes Principales Responsabilidad y Tecnologías
Presentación / Vistas Thymeleaf, HTML5 semántico, CSS propio (tokens.css + common.css + uno por área), iconos Lucide servidos en local, Leaflet + OpenStreetMap Vistas responsivas con modo oscuro, vistas Tarjetas/Lista en escritorio, agenda Mes/Semana, mapa de centros y diálogos propios (Cuquora.confirm/Cuquora.alert).
Seguridad SecurityConfig, AppUserDetailsService, GoogleOidcUserService, JdbcRememberMeTokenRepository Login por formulario o con Google, «Recordar mi sesión» 14 días, CSRF, rutas por rol (/client/**, /worker/**) y 404 propia también sin sesión.
Controladores Web & API Un controlador por área: ClientBookingController, WorkerCalendarController, WorkerAppointmentApiController, InventoryController, ClientCardController, CenterApiController… Controladores finos: reciben el formulario (record), llaman al servicio y eligen la vista. Los endpoints JSON (@ApiEndpoint) devuelven los errores también en JSON.
Lógica de Negocio (Servicios) BookingService, AgendaAvailabilityService, AgendaBlockService, ClientCardService, InventoryService, ProductSaleService, LoyaltyService, TreatmentSummaryService, CenterRegistrationService, InvitationService, CenterPhotoService, UserService, ClientNotificationService Toda la validación vive aquí y lanza BusinessRuleException (mensaje en español) o ResourceNotFoundException (404). BookingService concentra todos los cambios de cita con bloqueo por centro.
Integraciones mail/ (EmailGateway, AppointmentMailService, CenterOnboardingMailService), googlecalendar/, scheduler/, Nominatim (dirección a partir del pin del mapa) Correos de citas, contacto y alta de centros por SMTP (Brevo) o por consola; sincronización con Google Calendar de trabajadores y clientes en segundo plano tras cada cambio de cita (AppointmentChangedEvent); tarea cada 60 s que completa citas pasadas, caduca propuestas y envía recordatorios.
Acceso a Datos (Repositorios) Spring Data JPA Consultas por centro (findByIdAndCenterId) y @EntityGraph para evitar consultas N+1; open-in-view desactivado.
Persistencia & Datos PostgreSQL 16 (Docker) o H2 en memoria (desarrollo y tests) Esquema creado por Flyway (db/migration/V1 a V13) con ddl-auto=validate; datos demo solo con crm.seed-demo-data=true.
💡
Principio de Aislamiento por Sede:

Cada centro de belleza dispone de su propio almacén de inventario y sus propios tratamientos asignados. El catálogo de productos es global, pero las existencias, umbrales y alertas se calculan de manera independiente por cada sede física. Un trabajador solo puede ver y modificar datos de su centro: cualquier recurso de otro centro responde 404.

Se llevó a cabo una reorganización integral para que cada plantilla HTML importe única y exclusivamente los estilos que consume:

Auditoría Arquitectónica de Principios SOLID

Evaluación del diseño orientado a objetos del backend Java / Spring Boot

Se ha completado una inspección rigurosa del código fuente del backend frente a los 5 principios fundamentales de diseño de software (SOLID), detectando los siguientes puntos de fricción arquitectónica y sus planes de refactorización recomendados:

✅
Estado a 16 de octubre de 2026:

La mayor parte de los hallazgos se resolvió en la refactorización del 6 de octubre: BaseController y AppointmentController se dividieron en un controlador por área; ningún controlador usa repositorios (salvo DevLoginController, que solo existe en dev); los roles los gestiona Spring Security; el horario está en OpeningHoursPolicy (crm.booking.*); las reglas de cita están en BookingService; el mapeo a DTO está en AppointmentCalendarMapper; las plantillas de ficha tienen su propio ClientCardTemplateService; y ObjectMapper se inyecta desde JacksonConfig. Queda pendiente separar los servicios en interfaces por caso de uso.

S — Single Responsibility

Responsabilidad Única

Hallazgos:

  • BaseController orquesta landing comercial, validación de registro de usuarios, autenticación en sesión HTTP y simulador de depuración.
  • ClientCardService procesa serialización JSON de plantillas, operaciones CRUD de fichas y consolidación analítica de clientes a partir del histórico.
  • AppointmentService mezcla validación de horarios y persistencia con mapeo manual de entidades a AppointmentCalendarDTO.
Remediación: Separar en LandingController, AuthController y DevSessionController; extraer AppointmentMapper y desacoplar ClientCardTemplateService.
O — Open/Closed

Abierto para Extensión / Cerrado para Modificación

Hallazgos:

  • Bifurcaciones if/else basadas en Strings ("CLIENT" vs "WORKER") en controladores; agregar un rol (ej. ADMIN) obliga a modificar código existente en múltiples clases.
  • Horarios laborales (L-V 09:00 - 20:00, slots de 30 min) hardcodeados en el método privado isWithinOpeningHours de AppointmentService.
  • Reglas de notificación (stock ≤ 3, citas pendientes) centralizadas en un solo método rígido en NotificationService.
Remediación: Implementar patrón Strategy con interfaz NotificationProvider, extraer SchedulePolicy asociada a la entidad Center y gestionar roles con Spring Security GrantedAuthority.
L — Liskov Substitution

Sustitución de Liskov

Hallazgos:

  • Inyección de identidades fijas en la simulación de sesión de BaseController (asignación estática de ID 3L sin validar existencia previa en BD).
  • ClientSummaryDTO modelaba indistintamente clientes registrados y fichas sin usuario, obligando a verificaciones defensivas != null para prevenir NullPointerException.
Remediación: Emplear un contexto de sesión fuertemente tipado (UserSessionPrincipal) con invariantes garantizados.
I — Interface Segregation

Segregación de Interfaces

Hallazgos:

  • Ausencia de interfaces en los servicios de negocio (AppointmentService, ClientCardService, etc.); los controladores se acoplan a la clase concreta completa.
  • Interfaces amplias en repositorios: AppointmentRepository agrupa 14 métodos con propósitos muy distintos (operativa de reserva, analítica, agenda y borrado masivo).
Remediación: Descomponer servicios en interfaces orientadas al caso de uso: AppointmentBookingService, AppointmentScheduleQueryService y AppointmentManagementService.
D — Dependency Inversion

Inversión de Dependencias

Hallazgos:

  • Los controladores dependen directamente de implementaciones concretas en vez de abstracciones o contratos (IAppointmentService, IUserService).
  • ClientCardController inyecta y consulta directamente ClientCardRepository, saltándose por completo la capa de servicio (bypass arquitectónico).
  • ClientCardService instancia directamente new ObjectMapper() en lugar de inyectar el bean administrado por el contenedor IoC de Spring.
Remediación: Inyectar ObjectMapper a través del constructor, encapsular los repositorios exclusivamente dentro de servicios y desacoplar controladores mediante interfaces.

Modelo de Dominio y Entidades

Estructura relacional de base de datos que sustenta la plataforma

🏢 Center (Centros de Belleza)

Representa una sede física. Contiene nombre, dirección física, teléfono, email de contacto, coordenadas (latitud y longitud) para el mapa y la distancia, zona horaria (time_zone), número de cabinas (citas a la vez, de 1 a 50), CIF/NIF, si está publicado (los dados de alta nacen ocultos hasta que administración los revisa), la configuración de la tarjeta de puntos (loyalty_*) y la fecha de su foto (photo_updated_at; la imagen va en center_photos).

👤 User & Role (Usuarios y Roles)

Entidad de usuarios del sistema. Posee nombre, email único, teléfono, contraseña cifrada en BCrypt (nula en clientes dados de alta a mano y en cuentas solo de Google), google_id si ha entrado con Google y un Role (CLIENT o WORKER). Los trabajadores se vinculan a un Center.

💆 Treatment (Catálogo de Servicios)

Tratamientos ofrecidos por cada centro. Incluye nombre, descripción, tarifa (€), duración estimada en minutos (30, 45, 60, 90) y tipología (FACIAL, MASAJES, MANICURA_PEDICURA, CORPORAL, etc.).

📦 Product & Inventory (Insumos y Stock)

Product es el catálogo maestro (nombre, descripción, categoría, PVP). Inventory gestiona las existencias en cada sede con restricción de unicidad (center_id, product_id).

📋 ClientCard & Template (Fichas Técnicas Dinámicas)

Motor de fichas técnicas personalizadas por centro. ClientCardTemplate almacena en JSON la estructura de campos configurables (soportando tipos text, textarea, select, checkbox, date y el nuevo tipo number). ClientCard almacena las respuestas y notas técnicas del especialista por cliente.

📅 Appointment (Citas y Reservas)

Registra el turno acordado. Vincula un dateTime (fecha y hora exacta), un treatment, un center y obligatoriamente un client registrado (cuenta de usuario activa), el worker asignado, su estado (PENDING, PROPOSED, CONFIRMED, REJECTED, CANCELLED, COMPLETED), el workerMessage, el último cambio y quién lo hizo (last_change), la hora anterior si el centro la movió, los eventos de Google Calendar del trabajador y del cliente y el resumen del tratamiento (treatment_summary, con treatment_alert si es un aviso para próximas citas; solo lo ve el centro). El flujo de clientes invitados se suprimió para garantizar la trazabilidad de las fichas.

🕒 AppointmentProposal & AgendaBlock

AppointmentProposal: hasta 3 horas que el centro propone para una cita PROPOSED. AgendaBlock: bloqueos de agenda de un profesional (vacaciones, descansos) o de todo el centro si no tiene profesional.

🔗 GoogleCalendarLink & persistent_logins

GoogleCalendarLink: trabajadores y clientes con Google Calendar activado (token cifrado e id del calendario «Cuquora»). persistent_logins: dispositivos con «Recordar mi sesión».

🛍️ ProductSale & LoyaltyMovement

ProductSale: venta de un producto del inventario a un cliente, con la cantidad y el precio del momento (unit_price); al anularla se devuelven las unidades. LoyaltyMovement: puntos ganados (por una venta o por una cita completada, que solo suma una vez) y canjeados, por centro y cliente.

✉️ AccountInvitation & CenterPhoto

AccountInvitation: invitación de un solo uso (7 días) para que un trabajador de un centro nuevo ponga su contraseña; solo se guarda la huella SHA-256 del enlace. CenterPhoto: la foto del centro como JPEG de 1200 px como mucho, guardada en la base de datos.

Puesta en Marcha del Proyecto

Instrucciones para levantar la aplicación en entorno local o mediante Docker

Opción A: Ejecución con Docker Compose (PostgreSQL 16)

Primero copia .env.example a .env y rellena los secretos: docker compose no arranca si falta POSTGRES_DB, POSTGRES_USER, POSTGRES_PASSWORD o REMEMBER_ME_KEY. El esquema lo crea Flyway al arrancar.

# Desde la raíz del proyecto
cp .env.example .env      # y rellenar los valores

docker compose up --build -d
docker compose logs -f app

La aplicación estará accesible en: http://localhost:8080. PostgreSQL no publica puerto: solo lo ve la app dentro de la red de Docker.

Opción B: Ejecución Local con Maven y Java 21 (perfil dev)

# Windows (wrapper local)
mvnw.cmd spring-boot:run -Dspring-boot.run.profiles=dev

# Linux (Maven del sistema)
mvn spring-boot:run -Dspring-boot.run.profiles=dev

# Tests (167)
mvn test

Con el perfil dev la aplicación usa H2 en memoria, carga los datos demo con DatabaseSeeder y activa /login-selector y la consola H2. Sin SMTP configurado, los correos se escriben en la consola. «Iniciar sesión con Google» y Google Calendar solo aparecen si están las variables GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET y GOOGLE_TOKEN_KEY.
